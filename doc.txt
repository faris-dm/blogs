project


— a small community feed app

The pitch (keep it simple on purpose): Users sign up, follow other users, post short text/image posts, like and comment on posts, and see a feed of posts from people they follow. Think a stripped-down Twitter/Instagram feed — no need for stories, DMs, or algorithms. The simplicity of the idea is intentional — I don't want you burning time on scope, I want you burning time on getting the hard parts right.

Why this project, specifically — the hard parts hiding inside it
The feed query itself — "show me posts from people I follow, newest first, paginated" is a deceptively hard SQL problem once you have real data volume. This forces you to actually think about indexes, N+1 query bugs, and pagination — the stuff that makes apps "feel slow" in real life.
Likes — this is a race condition disguised as a checkbox. Two rapid clicks on "like" (sound familiar?) can create duplicate likes if you don't design the database correctly. Same disease as the duplicate order bug, different symptom.
Follow/unfollow — ownership and authorization again: can I unfollow someone on your behalf by guessing IDs? Can I see a private account's posts by hitting the API directly, bypassing your UI's "follow to see posts" logic?
Comments and posts — full CRUD with the ownership rule baked in: can only the author edit or delete their own post/comment. You will 100% mess this up at least once, and that's fine — that's the point.
Rate limiting — what stops someone scripting 10,000 posts a second? This introduces you to a concept we haven't touched yet, and it's a real production concern.

Based on everything today, here's your checklist — run through this every time before/while writing a route:

Before writing any route
What HTTP method? GET (read, no changes) / POST (create) / PUT (edit) / DELETE (remove)
What comes from the client, and where? req.body (form data), req.params (URL, like :id), req.query (like ?page=2)
What should NOT come from the client, even if it seems related? (e.g. user_id — never trust the client to say who they are; get it from req.user.id via auth middleware instead)
Does this route need Auth? If it changes data or shows private info — yes. If it's public read-only — no.
Does this route need an ownership check? If yes: WHERE id=$1 AND user_id=$2, in BOTH the lookup and the actual UPDATE/DELETE — never just one.
While writing the SQL
Does every UPDATE/DELETE have a WHERE clause? No WHERE = affects every row. Check this every single time, no exceptions.
Are you using $1, $2... with a params array? Never string-concatenate user input into SQL.
Does the WHERE clause match what the params array actually contains, in order?
Validation
What's the worst thing someone could send in this field? Empty? Negative? Too long? Wrong type? Someone else's ID?
Is this a client mistake (400) or a "doesn't exist" (404) or a "not yours" (also 404, don't leak which)?
Are two failure cases that shouldn't leak info returning identical messages/codes? (e.g. wrong password vs unknown email)
After writing
Re-read the exact lines flagged as wrong before, not just the new code. Old fixes get lost if you don't verify them.
Does every response have the same shape ({ success, message, data })? Consistency matters for the frontend.
Did you actually test it, or does it just "look right"? Run it, check real output, check the database directly.
